## 1. Purpose & scope

A single-page web tool where a miniature painter **picks or explores a colour** — a paint they
own, a chosen main/accent colour, a target hex, or by dragging an interactive wheel — and gets:

1. **Color harmonies** — complementary, analogous, triadic, split-complementary, tetradic — generated from that paint's color.
2. **Ideal vs. actual** — for every harmony color, the *theoretical ideal* swatch **and** the *nearest real paint you can actually buy*, matched by perceptual color distance (ΔE 2000), with a quality badge.
3. **Cross-brand equivalents** — the picked paint's closest matches in other brands (Citadel ↔ Vallejo ↔ Army Painter ↔ P3 ↔ …).
4. **Accessibility** — color-blindness simulation (protan/deutan/tritan) and WCAG contrast checks across the built palette.

### In scope (v1)
Client-side only. Static files. Works embedded in a Squarespace page via iframe.

**Entry modes** — all feed one engine (full breakdown in [`docs/USE_CASES.md`](docs/USE_CASES.md)):
start from an owned paint, a chosen *main* colour, a chosen *accent* colour, an arbitrary hex,
an interactive **drag-the-wheel** exploration, or a shared URL.

**Two temperaments, both first-class:** deliberate **planning** (persona Priya) and live
**exploration** (persona Sam — drag a node and the whole scheme + nearest real paints update in
real time, the Adobe-Color feel).

**Role-aware output:** harmony colours map to miniature paint *roles* — primary / secondary /
accent / metal / shade / highlight (~60-30-10) — each shown as ideal-vs-actual. Each slot also
gets a **derived wash + highlight** paint in v1; deeper multi-step ladders are a later enhancement.

**v1 conveniences (confirmed):** arbitrary **hex input**, a **'paints I own'** filter,
**compare two schemes**, and **export** to a shopping list.

### Added in v2
- **Colour-from-photo (photo eyedropper).** Pick a colour from a local image to seed a scheme — drawn to
  a canvas and sampled (3×3 average) **entirely on-device; the image is never uploaded** (consistent with
  the local-only, no-backend posture). Single-pick → seed; a dominant-colour "palette from photo" is a
  later enhancement. *(A live-camera eyedropper is a native-app feature — see `docs/IOS_APP_PLAN.md`.)*

### Out of scope (v1) — do not build without updating this file
User accounts, server/database, payments, paint inventory sync, a "buy" checkout,
native mobile apps, AI color suggestions.
These are parked in [`docs/PLAN.md`](docs/PLAN.md) §Future; a native iPhone app is explored
separately in [`docs/IOS_APP_PLAN.md`](docs/IOS_APP_PLAN.md) (v2 only) and governed by its own
constitution, [`CLAUDE_NATIVE.md`](CLAUDE_NATIVE.md) (active since Stage 1 began on 2026-10-29, when the
`ios/` platform folder was committed).

### Non-negotiables
- **No backend.** Everything runs in the browser. The dataset is a static JSON file.
- **No external runtime dependencies** unless added to §6 by name with a reason.
- **WCAG 2.1 AA** for the UI itself (the tool that checks accessibility must be accessible).
- **Attribution is mandatory** (see §5). The data is a curated compilation; we credit sources.

## 2. Product principles

1. **The paint is the hero.** UI chrome is neutral and quiet so real colors read true. We never tint swatches with our own styling: **every pixel of a swatch's colour field is the paint's hex** — no gradient, no sheen, no overlay (PLAN §5 item 51, Ryan 2026-10-30; the old finish overlays moved the colour by up to ΔE 10.4). A flat hex cannot show a finish, so a non-flat paint's swatch carries **one finish icon** in the swatch's own ink (§3.5 Swatch) and its row a **finish tag**: a suggestion is never mistaken for flat paint.
2. **Honest about approximation.** Hex values for physical paint are *approximate*. We always show the match quality (ΔE) and never imply a perfect match. "Ideal vs actual" is the whole point — surface the gap, don't hide it.
3. **One click to value.** Pick a paint → see a usable palette. No setup, no login, no wizard.
4. **Explain, don't mystify.** Every number (ΔE, contrast ratio) has a plain-language label in a painter's words ("excellent match", "weak: close in light and dark"; UX review F20: "Fails AA" is a rule for text on a screen). The Accessibility tab's contrast keeps WCAG's limits (4.5 and 3) and shows the ratio as the detail; its words say only what the ratio measures, light against dark.
5. **Portable & durable.** It must keep working as a dumb static file for years. Favor boring, standard tech.

## 3. Design system (the cohesive ethos)

Aesthetic: **Workbench+ — two themes, one instrument** (Ryan, 2026-10-28; `mockups/visual-identity.html`:
the old look read as "made by AI"). It is a painting desk, not a dashboard: small radii, hairline rules and
space in place of cards, condensed headings, dense tool-like controls. The tool ships a **light** theme
(*Workbench* — warm paper greys, a real paint as the accent: Citadel Sotek Green; the default) and a
**dark** theme (*Grimdark Tabletop* — forge-dark, flat brass accent; on-theme for wargamers). Both share **one
component system** — the *same* fonts, buttons, spacing, radii and motion — so only colour
changes between them. The colour always comes from the paint data; chrome stays quiet.

**These tokens are canonical.** Production CSS defines the shared tokens once and the two
colour sets as `:root`/`[data-theme="light"]` and `[data-theme="dark"]`. Do not introduce
off-token colours, sizes, or radii, and never style a component differently per theme — unify it.

### 3.1 Colour tokens — shared shape, two colour sets
Component tokens (radii, fonts, `--tap`, motion) are shared — see §3.3–3.4. Only the colour
sets below change between themes.

**Both themes are v1.** Light is the default. We follow `prefers-color-scheme` (live, while the app is
open) until the painter picks a theme with the `◐` control; only that pick is saved. The way back is
**⋯ → Use device setting**: a text action in the Theme row's reserved slot (where "Follows your device"
shows while the app follows the device). It shows when a theme is saved, and also when a link's theme
differs from the device's; it clears both, applies the device's theme and follows it live again. The OS
default and a shared link's theme are applied, never saved. The address bar carries `t` only for a link's
theme, the one theme a reload cannot get back otherwise (a device or saved theme written as `t` came
back over a newer device theme or saved pick); **Share link** adds `t=dark` whenever the scheme shows dark. Author every rule with variables — never hardcode a hex
outside these blocks. A swatch's own colour is paint *data*, never a token.

### 3.2 Match-quality scale (ΔE 2000) — fixed mapping, reuse everywhere
| ΔE 2000 | Label | Token |
|--------:|-------|-------|
| ≤ 1.0 | Indistinguishable | `--success` |
| ≤ 2.0 | Excellent | `--success` |
| ≤ 3.5 | Good | `--success` |
| ≤ 5.0 | Fair | `--warning` |
| ≤ 10  | Loose | `--warning` |
| > 10  | Poor | `--danger` |

**One limit on the words (PLAN §5 item 68; `data.js swapQuality`):** in the Shelf list's Not on the rack? swaps,
a **translucent** paint never says more than **Good**, also at ΔE 2 or less. Its hex is the least sure value in
the data: some lines hold the colour of a thin coat on white, others the colour in the pot. The ΔE shown stays
the true one, and one line before the list says these colours are rough. This covers an ink, a Contrast paint
and a glaze. **A wash or shade does not use this table there at all:** its swaps show **the gap** in degrees
with three words of its own, on the same three tiers (`data.js gapQuality`; §7):

| The gap | Label | Token |
|--------:|-------|-------|
| ≤ 4° | Close colour | `--success` |
| ≤ 8° | Near colour | `--warning` |
| > 8° | Other colour | `--danger` |

Both go when the wash colours follow one rule (`docs/COLOUR_CHECK.md`).

**A second limit on the words (PLAN §5 item 79; `scheme.js OWN_METAL_QUALITY`):** in the **Metal role**, a
metallic that the painter **owns**, within ΔE 15 of the role's target (the reach of the rule in §7), never
says Fair, Loose or Poor. It says **A metallic you own**: plain words in `--text-muted`, with no dot and no
state colour (`ui.js qualityWord`, `.qplain`; a neutral tag in the share image), and with no "No pot within ΔE
10" note and no advice to shift the hue. Its ΔE shows as before, and it is the true one (§2). Why: the
distance is to a colour that the app chose for "a silver", not to one that the harmony made, so "Leadbelcher ·
Poor" read as "your silver is a poor silver". A word of the success tier (Good or better) stays. An owned
metallic further than ΔE 15 keeps its word (in **Only**, a silver on a gold part still says Poor), and so
does a held role's pot.

### 3.3 Typography (shared by both themes)
- **Display / headings / wordmark:** `"Barlow Condensed", "Arial Narrow", system-ui, sans-serif` (600/700). Condensed and tool-like — a label on a rack, not a SaaS headline (the audit counted Inter + Space Grotesk among the "made by AI" signs).
- **Body / UI / labels:** `"IBM Plex Sans", system-ui, -apple-system, "Segoe UI", Roboto, sans-serif` (400/500/600). Engineered, clear at small sizes and in dense data.
- **Hex & ΔE:** `ui-monospace, "SF Mono", "Cascadia Code", Menlo, monospace`.
- Both webfonts are **self-hosted** (`src/styles/fonts.css` + `src/assets/fonts/*.woff2`, latin subset, `font-display: swap`) — no external requests — and both are under the **SIL Open Font License 1.1**, with each licence text beside the files (`src/assets/fonts/OFL-*.txt`) and a credit in About. About 116 KB for the five files. System fallbacks remain; the tool must look correct if a webfont fails to load.
- Scale: display 32/600 · h1 26/600 · h2 20/600 (Barlow Condensed is narrow, so its sizes run a step above a wide face's) · body 14/400 · small 12.5/400 · micro 11.5/500-caps-labels (`--text-muted`; `--text-faint` is 2.39:1 on the light surface, under AA, so it is not for text you must read).
- Line-height 1.5 body. Sentence case everywhere. No ALL CAPS except the 11.5px micro-label style (letter-spacing .05em).

### 3.4 Space, radius, elevation, motion
- Spacing scale (px): **4, 8, 12, 16, 24, 32, 48**. Nothing off-scale.
- Radius (unified, both themes; Workbench: small and few): panels and overlays `--r-card:6` · controls & buttons `--r-ctrl:4` · swatches `--r-sw:3` · tags `--r-tag:2` · `--r-pill:999` only for the round things (the theme switch, the slider's track, the Shelf handle, a scrollbar thumb). One radius vocabulary everywhere — never per-theme radii, never a raw px value. (Was 14 / 10 / 999 on everything: one soft radius was the first "made by AI" sign in the audit.)
- Elevation (Workbench: nothing in the page flow casts a shadow): **two** tokens — `--shadow` is only the small lift of a control that sits **on paint** (the live palette's buttons, the Shelf's state badge, the seed chip), so it shows on any colour; `--shadow-pop` is one crisp drop for what **floats** (the seed field's list, loupe, the mark menu, sheets — incl. the open phone Shelf panel and the ⋯ settings sheet or popover — the About and photo dialogs, the Restore / Delete confirms, toasts, the neutral note over the wheel); per-theme values in §3.1. A modal's backdrop is `--scrim`. No other shadow tiers, no bespoke box-shadows. A pinned bar (the Shelf dock) shows a 1px `--border` rule (`box-shadow: 0 1px 0`), not a shadow.
- Motion (shared, both themes) — **fades + gentle bounce, to confirm not decorate**:
  - Durations: 120ms hover · 180–220ms enter/exit & panel cross-fade · ~320ms card reveal. Standard ease `cubic-bezier(.2,.7,.2,1)`; **bounce/overshoot** `cubic-bezier(.34,1.56,.64,1)` for swatch & hero reveals.
  - Patterns: panels **cross-fade**; cards/role-slots **fade-rise** with a small stagger; swatches and the hero swatch **pop** (scale-bounce) when they appear or the scheme changes; buttons press to `scale(.96)`; the **Roll a scheme** d6 turns once on a press (320ms, the bounce ease, transform only, `element.animate()`): the scheme changes at the press and nothing waits for the turn.
  - **Only an action bounces.** A change the painter did not make (the neutral note folding to its ◐ pill) fades in 180ms, with no bounce. The regions rise only on load and on a Studio / Shelf switch, never on a re-render.
  - **Loading state:** the *Molten Harmonics* loader — a **determinate** drop → harmony-wheel → wells resolve that ends on the finished palette and maps to real load progress; seeded, themed via tokens, vanilla canvas (no runtime dep). Philosophy: [`mockups/loaders/MOLTEN_HARMONICS.md`](mockups/loaders/MOLTEN_HARMONICS.md). **Built** (`loader.js`, pure: one `p` draws one frame on a context it is given; `#loader` in `index.html`): it shows only when the paint data takes over **250ms** (a cached or bundled load never flashes it), under the header; its four wells are the **Recipe's own role targets** for the colour and harmony the link names (`roleIdeals`), its colours the page's tokens (`LOADER_TOKENS`), additive glow in dark only. The frame **eases toward the real download** (`loadDataset`'s `onProgress`: bytes over size, or a curve that never says done when the size is unknown) and never goes back; when the data is in, it finishes in about 0.4s **over the drawn app** and fades out in 200ms. It is a `role="progressbar"` (`aria-valuenow`); the canvas is `aria-hidden`. Under reduced motion it is **one still frame**, the finished palette, and only the progress line moves.
  - **Always honour `prefers-reduced-motion`**: disable transforms/animation and the loader loop (fall back to a single still frame). The CSS rule does not stop `element.animate()`, so a script that animates checks `matchMedia('(prefers-reduced-motion: reduce)')` itself (the d6 does not turn).
- **Layout stability — no jiggle.** Selecting, marking, hovering, or revealing controls must **never reflow** surrounding content. Express state with non-layout properties (`outline` / inset / overlay — not `border-width`; use `box-sizing: border-box` when a border width must change), **reserve space** for transient controls (fixed-height action rows; swap a hover tooltip for selection options in the *same* reserved slot), and float per-item affordances (tooltips, option popovers) as overlays. If a reflow is genuinely unavoidable, content shifts in **one consistent direction** — never a two-way jiggle. Especially the collection grid: marking owned/to-buy must not nudge neighbouring swatches.

### 3.5 Component rules
- **Swatch**: square, `--r-sw`, a 1px inset edge in `--sw-edge` (12% black in light so white-ish paints stay visible; 16% white in dark so near-black paints do). Text on a swatch is auto black/white by relative luminance — never a fixed color. **The colour field is the hex and nothing else** (§2). **The finish mark** (PLAN §5 item 51; `mockups/swatch-finish.html` round 2, variant a; Ryan 2026-10-30): a non-flat paint's swatch has **one icon, bottom-right, in the swatch's own ink** (`--ink` = `textOn`, as the copy button and the lock badge; 4.28:1 or more on every non-flat paint, in both themes, because it does not depend on the theme). It is opposite the mark badge's corner: state is a filled badge at the top, kind an outline icon at the bottom (two languages, below). **One icon per finish kind, from one table** (`data.js finishKind` + `FINISH_ICONS`: the paint's `fx` first, then its type): gem = metallic · drop = wash, shade, ink, glaze · drop with its lower half filled = contrast · ringed glint = gloss · drips = slime · dots = texture · a small sun = fluorescent · star = any other effect. A base or layer paint whose name says fluorescent or gloss has its icon and a tag with that word (dataset 1.11.0; `data.js finishWord`). The icons are the icon set's (a 20px grid, 2.25px stroke at this size). `fxCls(p)` gives the classes (`fm fm-<kind>`), `app.css` draws the icon as a mask (`--fm-*`, held to the table by a test), and the row's **finish tag** (`finishTag(p)`, a neutral tag: the same icon + the type's word) and the share image use the same table. Sizes: 12px, 2px in (28px swatches, the hero chip too); 3px in at 40px; 13px, 4px in on the Shelf's cells and the browse tiles; **none under 26px** (the Map's 10px pots, a 24px row swatch, the Schemes strip), where the row's tag or the paint's name says it. On the live palette the icon is the pot band's last item, after its hex; a target block is a colour, not a paint, so it has none. **Forced colours:** swatches keep their own colours (`forced-color-adjust: none`: the colour is paint data, not chrome), and the finish icon with them; the chrome inside one (a tooltip, a mark badge, the copy button) keeps the system colours; a ring round a swatch takes `Highlight`, and a ring drawn on the paint gets a `Canvas` band under it. The block is last in `app.css`, so it wins over the rings' own rules.
- **Roles** are **Primary · Secondary · Accent · Metal** (~60-30-10 + spot). With a limited collection two close-hued roles can't both get a distinct owned paint; the engine assigns distinctly where it can, and flags any forced reuse as a **shared paint** with how to differentiate (adjust direction) + the nearest distinct paint to buy.
- **Buttons (one style, both themes)**: primary = accent fill + `--on-accent` text; secondary = surface + 1px `--border`; ghost = text only. Radius `--r-ctrl`. **One main action per stage:** the primary button is `--tap` + 6px tall, 14.5px semibold, 18px each side, so it outranks the secondary buttons beside it (the audit's second sign was one size for every button). A button that starts with an icon keeps 10px on that side and 14px after its words. Height `--tap` = 38px with a mouse, **44px on any touch screen (`pointer: coarse`) or ≤520px**. Small buttons (`.btn.sm`) are 32px only with a fine pointer above 520px; on touch and on phones they are `--tap` too. Identical shape in light and dark — only colour differs.
- **Theme switch (`#themeToggle`)**: the one sanctioned **slide-over toggle** — the §3.1 `◐` control — `role="switch"` with `aria-checked` = dark. A thumb slides between a sun (light) and skull (dark, on-brand grimdark) with the icon cross-fading; the slide honours `prefers-reduced-motion` (state flips without animating). It looks 52×30 everywhere; a `::before` makes its hit area `--tap` tall (44px on touch), as on the Shelf handle, so the focus ring stays centred on the switch. This is the *only* toggle-switch in the system; every other either/or picker (theme had been one too, harmony, shelf filters) stays a **segmented control** (`.seg`). Don't add more switch-style toggles without a line here.
- **Segmented control (`.seg`, every instance — Studio / Schemes / Shelf, the Shelf's Grid / List / Map and the list's Rack order / By project, the harmony strip, the tone ladder, Use my paints, the Shelf status filter)**: a **joined toolbar** — the segments share 1px `--border-strong` borders and only the outer corners take `--r-ctrl` (no track, no pill, no shadow). Every label is **`--text`** (17.04:1 light / 13.89:1 dark on `--surface`). The pressed segment is an `--accent-weak` fill **with a 3px `--accent` bar along its bottom** (an `::after`, like the selected output tab's underline: 5.82:1 light / 5.54:1 dark against the fill); a hover is `--surface-2`; a press does not shrink the segment (its neighbours share its borders). **No weight change** and no layout property, so changing the selection moves nothing (§3.4). Segments are `--tap` tall on touch and ≤520px (30px with a mouse; in the ⋯ popover the whole control is `--tap` tall, as the buttons beside it). **Forced colours:** a `ButtonBorder` outline on each segment, a `Highlight` outline and bar on the pressed one; the focus outline sits outside, so focus and selection both show.
- **Slider (`#wl`, the wheel's lightness)**: the **only custom-styled range**. Its track is **paint data**: the pick's own hue and saturation from L 6% to 94% (`--wl-stops`, written on the input, never on `:root`), with a 1px `var(--text-muted)` edge so its ends show on any colour. The 28px thumb is filled with the colour now (`--wl-thumb`); its 3px ring follows the §7 text-on-swatch rule (`textOn`: `#15150F` or `#FFFFFF`, `--wl-ring`). Focus is a **2px `var(--accent)` outline**, offset 3px, as on the wheel canvas (the `--focus` colour, drawn as an outline). The input box is `--tap` thick, the hit area. **Forced colours** get `appearance: auto` (the system slider). Nothing animates and nothing reflows when its value or colour changes (§3.4).
- **Select (`<select>`, every instance — the Shelf's brand, type and sort, the seed list's Sort)**: with a fine pointer, where the browser supports it (`appearance: base-select` — Chrome and Edge 135+, Safari 27+), the app draws its own list **under the button** (`::picker(select)`, anchored to it, at least as wide as it; it opens above when there is no room below): `--surface`, 1px `--border-strong`, `--r-ctrl`, `--shadow-pop`, 4px padding. Each option's label starts exactly under the button's text, and the ✓ (`option::checkmark`, `--accent`) sits at the row's end; hover is `--surface-2`; the keyboard cursor is a 2px `--accent` ring inside the row. The chevron is `::picker-icon`: the icon set's own `chev` as a mask (`--chev-mask`, 16px, `--text-muted`, 12px from the edge; two rotated borders read as a check mark, Ryan 2026-10-29) and points up while the list is open; the open select gets the `--surface-2` fill (open is not focus). Touch keeps the system picker (better on a phone), a browser without support keeps its native select, and forced colours get `appearance: auto`. - **Tags (were badges/pills)**: square (`--r-tag`), a 1px border in the state's colour (or `--border-strong` for a neutral tag; the **finish tag** is neutral: a finish is a fact about the paint, and the metallic tag's warning colour said "Fair match"), the state's `*-text` colour, **no fill** (the shared class is `.tag` + `.success` · `.warning` · `.buy`; older tags keep their own classes) — the audit counted 20 weak-fill pills. Never remove outlines without a replacement.
- **State vs interaction — two separate visual languages.** Express what a thing *is* (owned, to-buy, ΔE quality) with persistent **badges / fills**; express what you're *doing* to it (hover, selected, focused) with **rings / outlines / elevation**. Never conflate the two (e.g. a coloured border that means both "to-buy" and "selected"). *Examples in code:* the **hero seed badge** (a `main`/`accent` pill on the picked-paint swatch) is *state* → a badge; the **seed docks** on the live palette unify the two languages deliberately — the pick's *tag* on a column ("⚓ Starting paint"; the paint's name is in its title, since the footer already shows it) is state, the dashed "⚓ Move here" dock on the other eligible column is the control that moves it (this replaced the toolbar Main|Accent toggle); a move says what it did (item 46: "Accent: the scheme now starts from the opposite colour, near Hydra Turquoise. Your paint stays as the accent."), and the starting paint's column in accent mode is tagged "Accent · your paint" ("Your accent (kept)" when it has no role); the **colour link** (hover/focus a Plan role card → ring the same colour's wheel node + live-palette column, and vice-versa, keyed by `data-hex`) is *interaction* → an outline ring (no reflow, §3.4). The seed badge lives on the **hero** (which always shows *your pick*), not the live-palette Primary column — that column is always the scheme's main, so a seed badge there would mislead in accent mode. The same interaction language extends to the **Equivalents drill-down**: on the Equivalents tab, clicking a live-palette column makes its colour the source whose cross-brand matches are listed, and that column keeps a *persistent* selection **ring** (a bolder ring than the transient hover link, and only on that tab) — interaction, not state, so it's an outline/ring, never a fill.
- **Semantic state colours are app-wide and single-meaning.** Owned, to-buy, and each ΔE-quality tier get **one** colour used everywhere it appears (its `*-text` shade is that colour darkened for legible text, not a second meaning) (collection, resolve, shopping list, future studio markers). Never overload one colour across two meanings — the to-buy colour must differ from the selection/marquee colour.

Both surfaces have **Paint details** (the paint detail sheet, above; on the Shelf for exactly one selected paint, in the seed list after the three marks). The Shelf adds **Start a scheme from this** on top: on for exactly one selected paint, it switches to the Studio seeded from that paint (focus on the Studio switch, never a text field); with 0 or 2+ selected it stays in the menu, `aria-disabled`, with the reason under its name, and says the reason when chosen. The Shelf's items stay `menuitem`s (they mark the whole selection). It opens on a **long-press** (500ms; a move over 10px is a scroll; the lift's click and compatibility mouse events are cancelled; on the Shelf on touch screens only, as before), a **right-click**, or **Shift+F10 / the ContextMenu key** (at the Shelf's cursor cell, or on the seed list's active option). Right-click: at the pointer; otherwise under the item, or over it when there is no room. The lift guard (a click in the first 350ms is the finger lifting, not a choice) is for touch and pen only. A press outside only closes it: it never also picks or marks. The Plan's buy toggles, the Equivalents drill-down and the Shelf's tap-to-cycle do not change. **Every mark repaints through one path, `render('marks')`** (app.js): the hero, the live palette and wheel, the active tab, the matching note, the seed field's open list and the Shelf; a hidden mode repaints when it shows.
- **Holds** (UC-3; `mockups/hold-flow.html` A, Ryan 2026-10-29): a role (Secondary · Accent · Metal; not Accent while the starting paint is the accent; never Primary) can be **held** in one of two ways, set on its Recipe card: **Lock colour** (a toggle, `aria-pressed`, a fixed name) keeps the role's target; **📌 Choose pot…** (the `pin` icon) opens the pot dialog (`#potDlg`, a modal `<dialog>` with the §3.5 header anatomy: a search field and `potRows`; for Metal the metallics come first), and a chosen pot shows as a neutral tag + **Change pot** + **Release**. - **Every interaction has a keyboard + screen-reader path.** Mouse-rich surfaces (the collection marquee / multi-select) provide keyboard equivalents (e.g. P/U/X + arrows, and **Shift+F10** or the **ContextMenu** key for the mark menu) and announce selection/state via `aria-live`. A live region is written only when its words change.

### 3.6 Responsive & mobile (must work on phones)
Embedded in a Squarespace page with heavy mobile traffic, so the tool is **mobile-first and
fully responsive**, not a desktop layout that merely shrinks.
- **Header is minimal (IA by stage, not by widget):** the header holds only the **Studio / Schemes / Shelf** mode switch + **⋯ Settings**, a dialog (not a menu; `aria-haspopup="dialog"`) in four **named groups, no submenus** (Ryan, 2026-10-28: each heading says what its buttons act on, and every action stays one tap away). **1:** **Use my paints** (off · prefer · only) — a setting saved for the device that ranks the live palette, the Plan, the shopping list and the Accessibility swap, never Equivalents; then **Brand** (Any · Prefer · Only, and a select with every brand in the paint data; `docs/TONE_LADDERS.md` B, Ryan 2026-11-06) — a setting saved for the device, built as Use my paints is and with the same scope (never Other brands): **Prefer** ranks the brand's paints 2 ΔE closer (§7), **Only** is a filter, and a role with no close paint in the brand shows the honest gap (§2). The select shows the painter's own brand, or else the brand they own the most paints of; with neither, "Choose a brand". The matches use a brand only after the painter chose it or turned the setting on with it shown (it is then saved), so a later mark on the Shelf never changes the matches by itself. Its hint is a reserved slot and a polite live region, as the Use my paints hint. Then **Theme** (the `◐` switch, with "Follows your device" or the **Use device setting** text action in a reserved slot left of it, §3.1); the **language follows the device** (`navigator.language`, live on `languagechange`), so ⋯ has no Language row (Ryan, 2026-10-28). **2, Share this palette** (the colours on screen now; a hint line says so): **Share image…** / **Share link…** / **Save the recipe** on touch; with a mouse **Copy image** / **Save the image** / **Copy link** / **Save the recipe** (the system share sheet only on touch, `CAN_SHARE` — Safari on a Mac had shown it on the desktop) — the whole-scheme output actions, secondary buttons (a shared link drops `m`, so a link shared from the Shelf opens the Studio; it keeps the tab `v`). **The image** (`shareimage.js`; `mockups/share-image.html` direction A, Ryan 2026-10-29) is a square 1080 px PNG of the four roles (pot + target band, name, brand · line, finish icon, ΔE + label), made on the device in the **theme on screen** (the page's tokens) — no server (§1). It is made when ⋯ opens, so the tap that shares it calls `share()` at once (Safari refuses a share whose tap is too old). **Share image…** gives the sheet the PNG and, in its text, the paint names and the link (a share has no alt field; some apps drop a `url` that comes with a file); with no file share it saves the file. **Copy image** copies the PNG only (a paste takes one thing; the image prints the address, and Copy link is beside it), hidden without `ClipboardItem`. **3, Your shelf on this device** (owned paints, the shopping list and settings, in one file): **Take to the store…** (the store panel, below; item 37) / **Back up everything** / **Restore…** — the whole-device backup of the `store.js` state (a `.json` file with its `saved` date); Restore…, and a `.json` picked through the Shelf's Import…, shows the same confirm before it replaces anything (CSV import and export are on the Shelf only). **4, Help & info:** **Help** (the Help sheet, §3.5, built from `support.html`) and **About** (with the **New** tag after an update, §3.5 What's new dot) (was "About & data": what the app is, **What’s new in** this version (`version.js WHATS_NEW`, at most 5 short lines), then **Earlier updates** (`version.js EARLIER_NEWS`: each earlier release's own lines under its version and date, newest first, from 1.13.0; a native `<details>`, closed at first, its summary a `--tap` text row with the `chev` icon), credits, links into Help, **Delete my shelf and settings…**, and the version line). A setting that changes the matches goes in ⋯ only when it is saved for the device, changes more than one stage, and changes the matches in a way you cannot see — so **Include Contrast** and the tone ladder stay in the Plan (Recipe) tab: they are saved for the device but act on that tab only, and you change them while you read it (Ryan confirmed, 2026-10-28, under the global-settings rule below). (Theme is a device-wide display setting, so it lives in ⋯ too.) Every other control lives in the stage it belongs to — the **seed field** (a paint or a hex, with **Browse** inside it) + **From photo** + **Compare** sit atop the Studio (the seed toolbar); the **seed's role** (Main|Accent) is set on the live palette itself via the **seed docks** (§3.5). **The rule (Ryan, 2026-10-28): a global setting, one that applies to the whole app, such as Theme, belongs in ⋯ in the header; a control that acts on one stage stays in that stage.** Don't move *per-scheme/in-stage* controls into the header; the only header actions are the whole-scheme **Save the recipe / Share link** and the whole-device **Take to the store… / Back up / Restore…**.
- **⋯ Settings: a sheet on touch, a popover with a mouse.** At `(max-width: 520px), (pointer: coarse)` (phones, touch tablets, a phone turned sideways) it is a **modal sheet** under the header: `showModal()`, `--scrim`, a fixed title row (**Settings** + **Done**, a rule under it), each label above a full-width control, every control `--tap` tall, and a bottom fade (opacity only, still under reduced motion) while more rows are below; a control that Tab (or "✓ Saved …") scrolls into view stops above the fade (`scroll-padding`). A button label may wrap (large text), never push its neighbour out. On a short screen (under 240px of room below the header — a phone turned sideways, or 400% zoom, WCAG 1.4.10) the menu covers the header instead, 8px from the top, and its rows scroll: a fixed dialog cannot be scrolled into view, so it never has a height floor. The search field's placeholder is "Search…" (its name stays "Search the shelf"). Brand · type · sort open as a **bottom sheet** (modal, Esc closes, focus returns). On open, focus goes to the sheet's **title**, never to a `<select>`: iOS opens a select's picker when it takes focus during a tap. Movement is transform-only (§3.4) and tucked controls are `inert`. The dock never hides while the search has focus or the sheet is open, and **every filter change scrolls the first results to just below the dock** (a filter applied deep in the grid must not leave a blank screen). **Swatch-name tooltips** show **one at a time** (the last input wins: the swatch you point at, or the keyboard cursor) and **flip below** the swatch when the header or the dock leaves no room above (the dock paints over the grid).
- **Paint picker = the seed field + a list that only picks** (`picker.js`; `mockups/paints-picker.html` "Recommended", Ryan 2026-10-28). It replaced the `☰ Paints` drawer and the `#` hex box. **One field** ("Paint or #hex", an APG **combobox**) takes a paint name, brand / line / type / finish words ("vallejo red", "citadel metallic", "dawnstone (layer)") or a hex: one matcher (`data.js` `paintMatcher` / `searchPaints`, the Shelf search's too) and one parser (`seed.js` `parseSeedQuery`). **Live hex:** "#" + 6 digits seeds as you type (also pasted); a bare `9A1115` or `#RGB` needs Enter (`#RGB` never seeds live); a hex word in letters only ("decade") searches names first, and "Use #DECADE as seed" is the last option; a paint name never becomes a colour. While a live hex is the seed, the polite live region says so (with any change of scheme it makes), and **Esc** closes the list and puts back the seed from before the typing; the colours typed since then leave the undo history. A pick (and the Shelf's Start a scheme from this) shows "Starting paint: …" as a toast, and the render's one announce says it first, then the mode note and the scheme (a `say()` after the render wrote over them). **Browse** (`Browse ▾` on a wide screen, a 44px grid icon inside the field ≤520px) opens the list **without the keyboard** (it never takes focus); the keyboard rises only when the painter taps the field. **The list exists only while open:** it is built on open from the current pick (never stale after a wheel drag), one tab stop (`aria-activedescendant`; the options never take focus). **Browse = a colour grid** (APG grid: `role=row` grouped by the column count that fits, grouped again on a resize; arrows in two directions): **Recent** picks first (this visit only, in memory — no new saved data), then every paint in the **Sort** order (Hue · Closest to your pick · Owned first · Name; the control comes right after the field in the tab order). **Search = listbox rows** (brand · line on each row; exact and starts-with names first; owned first in each group); a hex shows "Seed: #…" then the closest paints with ΔE and its label, ranked as Equivalents ranks a flat colour (`closestPaints`, FINISH_PENALTY), each with its TRUE ΔE. Tiles and rows reuse `.sw` + `fxCls` (the finish icon on the swatch), `finishTag` on a row, `markBadge` and `pname` (twins stay apart). **A tap or Enter only picks** and closes; marking is the mark menu (§3.5). It floats over the Studio as an **overlay** (absolute → no reflow, §3.4), under the field (the toolbar card's width on a phone; ≥440px under the field on a wider screen, the browse view ≤600px tall there), and **whenever it covers content it has `--shadow-pop`** — it always does while open (Ryan, 2026-10-28: "shadow whenever covering paints"; the Shelf dock's rule); the closed field has no shadow. **Motion:** it fades in (opacity only, 200ms); under `prefers-reduced-motion` it just appears. Its height comes from **`window.visualViewport`** (iOS does not shrink the layout viewport for the keyboard), recomputed on its resize and scroll; with too little room under the field, the page scrolls the field up first. **Short screen** (under 240px of room below the header — 400% zoom, a phone turned sideways; the ⋯ sheet's rule): the field goes to 8px from the top, the open list **covers the header** (the toolbar goes above it while open), and Sort scrolls with the paints, so one row of tiles and the cursor ring always show. A tile name may take three lines. A tap pick on a touch screen drops the keyboard and parks focus on the hero line (the one readout of the colour; a landing spot with no ring); after a key (a tablet keyboard too) or a mouse, focus stays in the field, where Ctrl/⌘+Z undoes the pick while the field is empty and the list closed. A tap on a field that holds text opens its results again. The field and Browse are a full `--tap` tall (both run over the field's 1px border). The Shelf remains the full-screen grid for bulk collection work.

It is every such load, not only a first visit (the old fixed start, the data's first row, was arbitrary too). The first render writes it to the address bar, so a reload keeps it. When the link **named** a paint or a colour that this build does not have, a toast and the live region say so ("This link's paint is not in the app. Here is a different paint."; UX review F18), because the scheme on screen is not the one that was shared.
- **First run** (UX 1): when the device has nothing saved (`store.firstVisit`, read before any write) and the link names no paint (`p`/`c`), a **"Start a scheme"** band sits under the seed toolbar: one sentence, four starter paints, three steps, and a text action to the Shelf (it opens the Shelf's **list**, as its index: item 78; the grid was 3,375 squares with no names). The first `render()` that changes the scheme ends it, and `store.keep()` saves, so it never comes back (Delete makes the device new again). It is a region (a rule under it), not a card.
- **The offer of Use my paints** (PLAN §5 item 76; UX review F01, rated 4 by all three raters; Ryan 2026-11-17): a painter marked 45 paints, and the scheme still ignored them, because the setting is Off, in ⋯, and nothing pointed to it. So the Studio asks **once**, in a band under the seed toolbar (`#umpOffer`; the first-run band's place and look: a region with a rule under it, not a card): "Use your paints in your schemes?", one sentence with the count ("You marked 45 paints as owned…"), then **Prefer my paints** (the band's primary button) · **Only my paints** · **Not now** (a text action), and one hint line that says what each does and that ⋯ changes it. It shows **when the Studio opens** (a mode switch, or a load) with at least one owned paint, the setting Off and no answer yet (`app.js umpOfferDue`), and never at the moment of a mark: a band that came in then would push the wheel down under the painter's finger (§3.4). An answer sets the setting (the matching note then shows it), says so in a toast, puts the focus on the hero line, and ends the offer for good; a change of the setting in ⋯ ends it too (`store.js` pref `umpAsked`, saved for the device and in a backup; Delete makes the device new again). The control itself stays in ⋯ (the global-settings rule above): the band is an offer, not a second control.
- **Keep your shelf safe** (PLAN §5 item 77; UX review F08, rated 4 by all three raters; Ryan's iPhone check, 2026-11-18): the shelf is only in this browser. Safari can delete it after 7 days of Safari use with no use of the app (WebKit's rule), and on an iPhone the Home Screen app starts with an **empty** shelf: its storage is apart from Safari's (seen on Ryan's iPhone). Help said so, and a painter reads Help after the shelf is gone. So the app says it **once**, in the flow, when the shelf first holds real work (`app.js hasRealWork`: 10 owned paints, or a saved scheme): a band that is the **first thing in `<main>`**, so it shows in each mode (`#keepNote`; the first-run band's look: a region with a rule under it, not a card): "Keep your shelf safe", one sentence that says where the shelf is (`help.js shelfHome`: Safari and its 7 days · this browser · this app, for an installed web app; it chooses words only, §6), then **Back up now** (the band's primary button: the backup file, at once) · **How to keep it** (a text action: Help at "Where is my shelf saved?", `#shelf-saved`) · **Not now** (a text action; its toast says where Back up is). In Safari on an iPhone or iPad a hint line adds the Home Screen order: back up here first, then Restore… there. It comes in **only when a mode opens** (a mode switch, or a load), never at the moment of a mark (§3.4), and in the Studio it waits while the offer of Use my paints shows (one band at a time). **Back up now**, **Not now** or any backup (⋯ → Back up everything, a confirm's backup offer) ends it for good (`store.js` pref `keepAsked`, saved for the device and in a backup; it is set before the file is written, so a Restore of that file in the Home Screen app does not ask again). After one of the band's buttons the focus goes to the pressed mode button. The iOS app (Capacitor) has its own copy of the shelf and never shows it. **A backup also asks the browser to keep the data** (`navigator.storage.persist()`, `app.js askPersist`; also at load in an installed web app with real work): WebKit says persistent storage "might be excluded from eviction" and that it grants the request "based on heuristics like whether the website is opened as a Home Screen Web App", so it can help and it is no promise. Firefox asks the painter, so the request is never made before the painter acts. The backup file is the real copy.
- **Layout (Studio):** a full-width **seed toolbar** (seed field · From photo · Compare) tops the **single-column** workspace (max-width ~1440 — the picker is the seed field's overlay list, so the workspace spans the full width). On wide screens (>1024px) the workspace **splits into two columns: a sticky *studio* column** (condensed **hero** line + harmony **wheel** + **live palette** + the **matching note**) that stays in view, and a **tabbed output** column (**Plan·roles / Equivalents / Accessibility**) that scrolls beside it — the role plan's cards go **2-up** at this width. Side by side, the columns share three rows (colour · seed dock · paint) through a **subgrid**, so colour blocks, docks and paint names line up whatever each footer holds. The Plan tab is the *detail* for that bar (ideal→nearest paint + tone ladders; each ladder step shows its **pot** — the matched paint's colour with its finish icon — not the target) and **must not** re-draw its own duplicate colour bar. **The maker's ladder** (`ui.makerLadder`; `docs/TONE_LADDERS.md` A, Ryan 2026-11-06): when a role's pot is one tone of a maker's family (`data.js familyOf`), its card adds a last row, "Ultramar Blue · Tone Pro: the maker's 5 tones", "Blood Colors · Reaper triad: the maker's 3 tones" (dataset 1.12.0: 43 Reaper triads), "Browns · Army Painter triad: the maker's 6 tones" (dataset 1.13.0: the 27 Flexible Colour Triads of Warpaints Fanatic) or "Warm Brown · Two Thin Coats triad: the maker's 3 tones" (dataset 1.14.0: 43 triads; one that the maker gave no name, on its colour wheel, says only "Two Thin Coats triad: the maker's 3 tones"), every tone darkest first, as pots; the pot's tone says **your pot** (words and weight, state — never a ring); **no ΔE** (the maker's steps, not matches); a `role="group"` named "…darkest first", each tone a focusable step with its tooltip. The two columns are **one instrument, not two panels**: a **colour link** ties them — hovering/focusing a Plan role card rings the same colour's **wheel node + live-palette column** (and vice-versa), matched by `data-hex` (see §3.5). Keep them coupled — don't split the wheel and the plan into separate tabs/views.

The active chip auto-centres (the strip is `position: relative`, so a chip is measured from the strip's own edge).

- **Touch feels like an app, not a page** (`@media (pointer: coarse)` in `app.css`): text fields and selects are **≥16px** (iOS zooms the whole page when a smaller field takes focus); **double-tap zoom is off** (`touch-action: manipulation`) but **pinch-zoom stays** on the website (WCAG 1.4.4 — the iOS app blocks pinch natively); **no grey tap flash** (press feedback comes from `:active`, which iOS only applies with a `touchstart` listener present); and **controls aren't text-selectable** by long-press, while content text stays selectable.
- No horizontal page scroll; swatches and wheel scale fluidly. Verify at 360 / 768 / 1180px. **A grid column that holds a page is `minmax(0, 1fr)`, never a bare `1fr`** (`1fr` is `minmax(auto, 1fr)`: it grows to its widest content, and the Shelf list's sideways-scrolling store row made a 360px page 936px wide; PLAN §5 item 58; `test/ui.test.mjs` checks `main`).

Rules:
- `color.js`, `harmony.js`, `a11y.js` are **pure** (no DOM, no globals) so they are unit-testable.
- State lives in one place (`app.js`). UI reads state, emits events; no scattered globals.
- Palette/scheme state is encoded in the URL query (shareable, like Adobe Color) — no storage needed for sharing. Persistent personal data (owned + to-buy collection, prefs, and since v2 each to-buy paint's count and project and the kept schemes — `wantInfo` and `schemes`, two maps beside the v1 fields so a v1 build still reads the list; a scheme's id never changes, its share-link query is a field) goes through **`store.js`** only — one versioned, serialisable model (export/import JSON, paintRack-CSV-ready) so it can move from `localStorage` to IndexedDB / native / sync without touching callers. ⋯ → Back up / Restore… use that JSON (`exportJSON` with a `saved` date; `inspectJSON` reads a file without applying it; `importJSON` replaces); Delete is `clear()`, which removes every copy (`ps-state`, the legacy `ps-owned` / `ps-theme`, the iOS mirror). Each open tab takes another tab's save or Delete (the `storage` event, `onExternalChange`), so a tab with an old copy cannot write it back. No personal data leaves the device.
- The app is an **installable, offline-capable PWA**: `sw.js` cache-firsts the static shell + dataset (cross-origin fonts pass through, with the system-font fallback covering offline); `manifest.webmanifest` + `icon.svg` make it installable. This is the foundation for the future Capacitor app (`docs/IOS_APP_PLAN.md` approach A→B). Both `sw.js` and `i18n.js` are vanilla — no dependency (§6).
- **`i18n.js`** localizes **chrome strings only** — paint names are data and never translate. The locale follows the device (`navigator.language`), with no setting (a `locale` pref from an older build or a backup is ignored); en-GB is canonical, en-US a sparse spelling-override layer (`colour`/`color`). Mark static text `data-i18n` / placeholders `data-i18n-ph` / accessible names `data-i18n-aria` / tooltips `data-i18n-title` (and `data-i18n-html` only for the table's authored `*Html` strings — links and emphasis, never data); use `t(key, vars)` for dynamic strings (`{name}` placeholders).
- `mockups/` (design references) and `scripts/` (dev tooling) are **never** loaded by the app at runtime — they don't count against the no-dependency rule in §6.

## 5. Data model & licensing

The dataset is a **curated compilation** assembled from open-licensed community datasets and
manufacturer-published values — **not** a copy of DakkaDakka's page. We credit DakkaDakka and
upstream sources in-app (a "Data & credits" panel) and in `src/data/SOURCES.md`. Full sourcing &
verification methodology: [`docs/DATA_SOURCING.md`](docs/DATA_SOURCING.md).

### 5.1 Schema (`src/data/paints.json`)
```jsonc
{
  "version": "1.0.0",
  "generated": "ISO-date",
  "paints": [
    {
      "id": "citadel-base-mephiston-red",   // brand-line-slug, stable — made once and never changed (§5.2)
      "brand": "Warhammer Colour",             // the maker's current name (Citadel Colour until 2026; the id keeps "citadel")
      "line": "Base",                        // Base/Layer/Shade/Contrast/… or brand range
      "name": "Mephiston Red",
      "hex": "#9A1115",
      "type": "layer",                        // base|layer|dry|shade|wash|ink|contrast|glaze|effect|metal (finishes excluded from harmony suggestions; metal = Metal role)
      "discontinued": false,
      "approx": true,                         // is the hex approximate?
      "source": "community",                  // manufacturer | community | sampled
      "sourceUrl": "https://…",               // where the value came from
      "captured": "2026-06-24",               // date the value was recorded — provenance record, not shown in the UI
      "fx": "texture",                         // optional: gloss|slime|texture on an effect paint (its finish icon and its store swaps), or fluo|gloss on a base or layer paint whose own name says so (its icon and tag only: it stays a flat paint for every match) — build-seeded by keyword
      "formerly": ["Bugman Glow"],             // optional: earlier spellings of the name (a corrected name keeps the source's); search and CSV import match them
      "family": "citadel-tone-pro-ultramar-blue", // optional: the maker's family of tones (Tone Pro; Reaper's triads, "reaper-triad-09701"; The Army Painter's, "army-painter-triad-browns"; Two Thin Coats', "two-thin-coats-triad-berserker-red"; docs/TONE_LADDERS.md §6) — a stable id
      "tone": 3                                // with `family`: the paint's place in it, 1 = the darkest (for a Reaper or Two Thin Coats triad: the maker's order, shadow · midtone · highlight; for an Army Painter triad: 1 to 6)
      // "groupId" links a paint to its equivalence group in groups[] (auto-seeded ΔE≤1; see §5.2)
      // lab[] and dname (display name — carries the line when a brand reuses a name across lines,
      // e.g. "Dawnstone (Layer)" vs "Dawnstone (Dry)") are derived at load time, never stored. Manufacturer *release* dates
      // are not available from our sources; "captured" is the record date.
    }
  ],
  "groups": [
    { "id": "red-blood-01", "refHex": "#C21920", "label": "Blood red" }
  ],
  "families": [                              // only the families whose name is not in their paints' names (the makers' triads); `name` is the maker's, and is left out when the maker gave none (a Two Thin Coats triad on its colour wheel)
    { "id": "reaper-triad-09701", "name": "Blood Colors", "kind": "triad" }
  ]
}
```

### 5.2 Data rules
- Every paint **must** carry a `source` provenance entry in `src/data/SOURCES.md` (brand official vs community).
- `groups[]` is **auto-seeded at build time**: paints within ΔE 2000 ≤ 1.0 **and the same finish class** (metal · translucent wash/shade/ink/contrast/glaze · effect · opaque flat — a wash is never "interchangeable" with a flat that shares its hex, §2) are clustered (union-find) into equivalence groups (`{id, refHex, label}`), and each member paint carries a `groupId`. The Equivalents tab surfaces a paint's group ("Almost the same colour in the paint data (ΔE 1 or less)", with "compare the pots": a group is made from approximate hex values, so the app never calls its paints interchangeable, §2); the *closest other-brand* matches are still computed at runtime by ΔE 2000. Groups are regenerated by `build-dataset.mjs`, then corrected by hand via `src/data/group-overrides.json` (relabel / split / exclude, anchored by stable paint ids).
- **An `id` never changes**, even when a brand or a name does: saved shelves, backups and share links hold ids. When the maker renames a brand, the build keeps the old brand key in the id (`key` in `build-dataset.mjs`; Warhammer Colour's ids stay `citadel-…`) and its sort place (the order breaks exact ΔE ties). A corrected name keeps the source's spelling in `formerly`, and the id is made from that spelling. The brand's former name stays a search word (`data.js BRAND_WORDS`) and a CSV alias.
- `hex` is sRGB. `lab` is **derived at runtime** (D65) — do not store stale Lab.
- Mark `approx: true` unless the value is manufacturer-official; the UI shows an "approx" tag.
- Adding a brand = add rows + a credit line. Never scrape into the repo without recording the source and its license.

## 6. Coding standards

- ES2020+, modules, `const`/`let`, no transpilation assumed.
- **Dependencies: none at runtime, and zero third-party runtime requests.** The webfonts (Barlow Condensed, IBM Plex Sans) are **self-hosted** (§3.3), so the app makes no external calls at all. Tests use Node's **built-in** runner (`node --test` / `node:assert`) — no install, no devDependency. Anything else needs a line here.
  (One standing exception, active since Stage 1: the native track's **dev-only** Capacitor
  packages, allowlisted in [`CLAUDE_NATIVE.md`](CLAUDE_NATIVE.md) §4 — they never enter the web runtime.) We hand-roll colour math (it's small and well-specified) rather than pull a library.
- Pure functions for math; side effects only in `ui.js`/`app.js` and the app-injected DOM modules (`wheel.js`, `markmenu.js`, `picker.js`), which get state and actions from `app.js` and hold no scheme state of their own.
- Accessibility: semantic HTML, labelled controls, keyboard operable, visible focus, `aria-live` for dynamic palette updates, respects `prefers-reduced-motion`.
- Performance budget: first render < 100ms after JSON load; nearest-paint search over the full dataset < 16ms (precompute Lab once).
- Comments carry the *why*. A plain-English *what* is welcome too where it makes the code approachable
  to a reader new to it — but a comment must never drift from the code it describes: correct or delete
  it in the same commit as the code it no longer matches. A trailing comment on a code line couples the
  two in git (every annotated line becomes a modified line), so prefer a comment *above* the line when
  the note is more than a few words — a large trailing-comment pass conflicts with any later edit and
  goes stale invisibly where it doesn't (the lesson of PR #20, closed unmerged).

## 7. Color-science conventions (lock these so results never drift)

- **Conversions**: sRGB ↔ linear ↔ XYZ ↔ **CIELAB (D65)**. Matching is done in Lab.
- **Distance**: **CIEDE2000 (ΔE 2000)** with kL=kC=kH=1. This is the single matching metric.
- **Match ranking (v1.8)** may adjust the *ranking* — never the reported ΔE (§2 honesty): the owned-boost
  (−6), a **metal demotion for colour roles** (+4 — metallics read differently on the model; the Metal
  role's all-metal pool demotes all candidates equally so it's unaffected), and a **picked-paint
  tie-break** (−0.001 — the paint the user explicitly picked wins exact ΔE ties, e.g. Layer vs Dry
  twins that share a hex). Constants live in `app.js`/`data.js`; change them only with a CHANGELOG note.
  **The Metal role's own owned boost is 15** (PLAN §5 item 79; `docs/UX_REVIEW.md` §11; Ryan 2026-11-17;
  `scheme.js metalMatch`, `METAL_OWNED_REACH`). The Metal target is one of three fixed colours (gold, silver,
  gunmetal: `metalIdeal`), and the data has 244 metallics, so some pot is always within about 3 ΔE of it. With
  the boost of 6, a metallic that the painter owned never won: Leadbelcher is 10.3 from the silver, Retributor
  Armour 9.4 from the gold. With **Use my paints: Prefer**, an owned metallic now ranks 15 ΔE closer for this
  role alone. Measured on five shelves: an owned metallic is the Metal pot for 7% → 80% of schemes, with no pot
  of the wrong kind and none over ΔE 14.2 (a boost of 20 let a brass in for a gold; a rule by kind, read from
  the hex, put a bright silver on a gunmetal part). The reported ΔE stays true. A Metal role that the painter
  holds (a locked colour, a chosen pot) keeps the boost of 6: its target is their choice. The Recipe and the
  live palette's Metal column both call `metalMatch`, so they show the same pot.
  **The Brand setting (`docs/TONE_LADDERS.md` B):** with **Prefer**, a paint of the chosen brand ranks **2 ΔE**
  closer (`BRAND_BOOST`, data.js; measured there: the brand wins 54% of ladder steps against 14%, and the median
  true ΔE stays Good, 2.16 against 1.83). It is a second term beside the owned-boost: both add for an owned paint of
  the brand, and an owned paint of another brand (6) still wins over a paint to buy of the brand (2). The picked
  paint gets the same bonus, so it keeps its own slot. **Only** is a filter (`brands`), as Use my paints → Only.
  The mirror rule for **metallic sources**: when the equivalents source is itself metallic (a picked
  `metal` paint, or the Metal column's ideal), **true metallics rank strictly first** — a flat paint
  near the hex is not an equivalent of a metal on the model (`equivalents` metal tier · `nearestPaints`
  `floatTypes`; a metal's auto-seeded group also lists its metal members first). Reported ΔE stays true.
  **Equivalents rank by finish (Ryan, 2026-10-26):** a paint of a different **finish class** (§5.2: flat ·
  translucent · effect · metal; `finishClass`) ranks **+4** further (`FINISH_PENALTY`, data.js), so a wash,
  contrast or texture paint is offered as the equivalent of a flat one only when it is clearly closer, and a
  wash's list leads with washes. Role colours and custom hexes on that tab count as **flat** targets (the
  Metal column keeps its metal tier). A penalty, not a strict tier: a strict tier pulled 293 matches over
  ΔE 10 into wash lists. Measured: flat sources 78% → 99% same-finish matches, +0.27 mean ΔE.
  **Store swaps rank by kind (PLAN §5 item 71; `data.js swapKind`, `SWAP_KIND_PENALTY`):** in the Shelf list's
  Not on the rack? swaps, the finish class is strict (a wash's swap is a wash-class paint, or none). Inside the
  class the kinds are different products: wash and shade (one kind) · ink · Contrast · glaze; base and layer (one
  kind) · Dry. A swap of another kind ranks **+2** further (ranking only; the ΔE shown is true). An **effect**
  paint swaps only for one with the same `fx` (gloss · slime · texture · none): wet blood is no swap for a rust
  texture. Measured with every brand carried: a wash's or shade's best swap is a wash or shade for 69% (was
  40%), for +0.29 mean ΔE; a Contrast paint's is a Contrast paint for 86% (was 65%), for +0.21. It changes no
  other match: Equivalents keeps `FINISH_PENALTY`. **A swap the painter owns** (item 72; `SWAP_OWNED_MAX` = 3.5,
  the Good limit) goes first when its ΔE is 3.5 or less, whatever the Use my paints setting: with a good pot on
  the shelf there is nothing to buy. A looser owned pot keeps its own place (first place would say it is the
  best swap). The brand toggles do not limit an owned pot.
  **A wash against a wash: the gap (PLAN §5 item 68, way C; Ryan, 2026-11-17).** The makers show a wash in
  different ways (a thin coat on white, or the liquid in the pot), so two washes of one colour can be ΔE 50
  apart in the data. A wash is a clear coat: by the Beer–Lambert law a thicker coat has the same absorbance
  (−ln of each linear RGB channel, `color.js absorbance`; each channel kept in 0.004 … 0.996) in every channel,
  only larger. So the **direction** of the absorbance is the wash's colour and its **length** is the coat's
  thickness. In the store swaps, a wash or shade ranks the paints of its class by **the gap**: the angle between
  the two absorbances, in degrees (`absorbGap`), plus `0.02 × ΔE` to part two washes at one gap (`WASH_GAP_TIE`;
  all blacks and greys are near 0°) and **4°** for a swap of another kind (`WASH_KIND_GAP`: an ink, a Contrast
  paint, a glaze; at 4° the best swap is a wash or shade for 96%, at no cost in colour family). A paint that hardly absorbs (length under
  `WEAK_ABSORB` = 0.5: a white wash) has no clear direction: it is no swap by the gap, and as the paint to buy
  it keeps ΔE. An owned wash goes first when its gap is 4° or less. The words: **Close colour** ≤ 4° · **Near
  colour** ≤ 8° · **Other colour** over that (§3.2). Measured on dataset 1.9.0 against the colour word in the
  washes' names (106 of 131 have one; browns, fleshes, sepias and rusts as one family), the best swap is in the
  same family: every brand 65% by ΔE and 64% by the gap; Warhammer Colour + Army Painter 44% → 71%; Warhammer
  Colour only 32% → 74%. A pair under 4° is one family for 2 in 3, over 8° for less than 1 in 3. **The gap is
  for washes only, in two places:** the store swaps, and the second try of the Recipe's wash step (Wash-step
  media, below). The Equivalents tab uses ΔE.
- **Harmonies** are computed from the base in HSL. Most rotate **hue** (keeping S/L); the two *value*
  harmonies instead vary **lightness/saturation** at the base hue. Each partner is a locked `{dh,ds,dl}`
  step from the base (`harmony.js` `HARMONY_STEPS`):
  - complementary `+180°`
  - analogous `−30°, +30°`
  - triadic `+120°, +240°`
  - split-complementary `+150°, +210°`
  - tetradic (rectangle) `+60°, +180°, +240°`
  - square `+90°, +180°, +270°`
  - compound `+30°, +180°, +210°` (base + a neighbour + the complement + the complement's neighbour)
  - **shades** — same hue & saturation, lightness `−0.24, −0.12, +0.12, +0.24` (a value ramp)
  - **monochromatic** — same hue, saturation `−0.34, −0.17, +0.10` (with a touch of value)
  - **custom** — no rule (zero steps); the palette is whatever the painter builds by hand via the
    per-swatch lock/edit/add controls. The role plan still derives a Secondary (`+30°`) and an Accent
    (`+210°`) from base rotations, and the wheel and the live palette show both (`roleColours`, app.js), so
    no view shows a role that another view does not. On the wheel they are role nodes; a drag locks the role.
- **Roll a scheme (the d6, §3.6)** picks a harmony at random from a locked pool (`harmony.js rollHarmony`), never
  `custom` (it has no rule) and never the current one: a seed with a hue rolls from the **9 rule harmonies** (the 7
  hue rotations + shades + monochromatic); a **neutral** seed only from **neutral-pop · duotone · warm-cool · shades**.
  It changes the harmony only: the pick, its role, the lightness, the locked and added colours and the pop stay.
  A load with no paint in the link (§3.6, a random first scheme) rolls its harmony from the same 9 rule harmonies.
- **Adding a colour** (the live palette's `+`, "add along the line") extends the base's **value ramp** —
  alternating tints/shades stepping outward — rather than inventing a new hue.
- The wheel can only place **hue** partners on the ring, so for the value harmonies (shades/monochromatic)
  it shows just the base + any added/free nodes; the value ramp itself is read in the live-palette strip,
  and those partners are display-only there (no per-swatch lock/edit, since they can't be keyed by hue).
- **Neutral seeds (v1.8).** A seed with Lab chroma **C\* < 10** (`isNeutral`; perceptual, so visually-black
  "saturated" hexes like `#100000` classify correctly) has no usable hue: the studio enters **neutral
  mode** automatically (and reversibly — saturate the seed and it exits, restoring the parked harmony).
  Mode switching uses **hysteresis** (enter < 10, exit > `NEUTRAL_EXIT` = 14): a drag hovering on the
  boundary can't flip the mode per frame. A load (a reload or a share link) holds no mode yet, and the link
  has no mode in it. So in the 10–14 band, a neutral-only harmony in the link (neutral-pop · duotone ·
  warm-cool) starts neutral mode, and any other harmony starts hue mode (`harmony.js startsNeutral`). A
  reload then keeps the link's harmony. The one neutral explainer is a wheel **overlay** (never
  reflows, §3.4) that auto-collapses to a ◐ pill; the pill re-expands it. The overlay sits in a box that is exactly the wheel (`.wbox`), so it never covers the lightness slider.
  Hue-rotation harmonies grey out in place (visible + tooltip'd); the neutral-native schemes are
  (`harmony.js neutralPartners`, recipes locked; partners are ordered **[secondary, accent]** by
  construction — no ΔE-furthest rule, the pop *is* the accent):
  - **neutral-pop** (default) — bridge `hsl(popH, .07, L±.20)` + the **pop** (a chosen accent colour,
    default `#9C1626`, min S `.15`; wheel-draggable, URL param `pp`)
  - **duotone** — pop-family mid `hsl(popH, .30, L±.24)` + the pop
  - **warm-cool** — cool `hsl(222, .14, L±.16)` + warm `hsl(32, .16, L±.24)` tints of the seed (no pop)
  - plus **shades** and **custom**, which survive unchanged (value steps don't need a hue).
  `L±` steps *away* from the seed's end of the value range. A neutral seed always holds **Primary**
  (the palette's Accent seed dock disables with the why — a neutral accent has no complement) and its Metal ideal is
  always gunmetal `#6E7177` (no hue to read a temperature from).
- **Accent-seed pinning:** in accent-seed mode the **Accent role's ideal is the picked colour
  verbatim, in every harmony** (the rest of the scheme derives from the pick's complement). The
  180°-step harmonies land there by construction; without the pin, split-comp/analogous/value
  harmonies dropped the picked colour from the plan entirely.
- **Holds (v1.12):** a **locked** role's ideal is the held hex, in every harmony; the rest of the scheme
  derives as before. A **store swap** (item 38) is a chosen pot with `was`, the paint it replaced; the role
  carries it as `swappedFrom` and nothing else about the match changes. A **chosen pot** is the role's match whatever the ranking: its reported ΔE is measured
  from the role's *generated* ideal (the honest gap, §2), it is never reused by another role (its id is in
  `usedIds` first), and its tone ladders start from the pot's hex. A pot id not in the dataset acts as a lock
  on its stored hex.
- **The Shelf's map** (item 61) bins paints by Lab hue (the Browse order's 20° bands from 20°; C\* < `GREY_CHROMA` = grey) and
  Lab L\* (30 · 45 · 60 · 75). A tone's target is the mean Lab of the dataset's opaque paints still made in it; the pots that
  fill a gap rank by ΔE 2000 to that target alone, and the ΔE shown is the true one. It changes no match anywhere else.
- **The maker's ladder is shown, never matched** (`docs/TONE_LADDERS.md` §4.3): a role whose pot belongs to a
  maker's family carries the family as its own field (`role.family`), not as a ladder. The app's ladder steps are
  about two Tone Pro tones wide, so nothing is matched to the family, it changes no match and no ΔE, and the
  shopping list's walk of `ladders` never adds the family's tones.
- **Color-blindness simulation**: Machado et al. (2009) severity-1.0 matrices applied in linear RGB, for protanopia / deuteranopia / tritanopia.
- **Temperature ladder (v1.8):** a NEUTRAL colour role's card leads with **Cool · base · warm** — its
  value steps have no hue to walk, so the ladder walks temperature instead (locked absolute tints:
  cool `hsl(222,.12, L−.14)` · the ideal · warm `hsl(32,.14, L+.16)`); the selected value ladder(s)
  still follow. Saturated roles are unchanged.
- **A paint that is no longer made is not a suggestion** (`data.js passesFilter`; dataset 1.10.0 has the first four, the Gloss Shades). `nearestPaint(s)` skips a `discontinued` paint: the Recipe, the tone ladders and the shopping list offer only pots a painter can buy. It stays a match when the painter **owns** it (the owned set, in every Use my paints setting) or **picked** it (the starting paint). Lists of every paint keep it, with its tag: the seed field, the Shelf, Other brands. The store swaps have the same rule (§3.6).
- **Wash-step media (v1.8; the second try: PLAN §5 item 74, Ryan 2026-11-17):** the Wash·base·highlight ladder's
  *wash* step prefers REAL shading media (`wash`/`shade`/`ink` types, the finish exclusion lifted for that step
  only). Three tries, in order (`scheme.js washStep`): **(1)** the medium nearest by ΔE, within ΔE ≤ 10;
  **(2)** the medium nearest by **the gap** (`data.js washByGap`: the same pool, the gap + `0.02 × ΔE`; an owned
  wash first when its gap is 4° or less), within **8°** — the step then shows "gap 4°" as plain mono text beside
  its finish tag, with the reason in its title and its accessible name, and Save the recipe writes the gap on
  its row; the ΔE in the match stays the true one (§2); **(3)** the darkened-base match flagged **"watered
  down"** (thin the base) — never a silent substitution (§2). A target that hardly absorbs (a near white) has no
  gap. Measured on dataset 1.10.0 (1,882 base and layer paints with a colour word in the name): a real wash is
  found for 93% → 99% with every brand, 66% → 89% with Warhammer Colour + Army Painter, 8% → 79% with Warhammer
  Colour only; the washes the second try adds are in the paint's colour family as often as the ΔE ones (48–66%
  against 51–60%). ΔE stays first, so a Recipe that had a wash keeps it; 6% of all wash steps change from
  "watered down" to a wash.
- **NMM (non-metallic metal) ladder (v1.8):** the Metal role also offers a flat-paint recipe for the
  metal illusion — locked steps off the metal ideal: shadow `{dl:−.26, ds:+.04}` · mid (the ideal) ·
  highlight `{dl:+.30, ds:−.18}`, matched with metallics AND finishes excluded.
- **Contrast**: WCAG 2.1 relative-luminance ratio; AA thresholds 4.5:1 (text) / 3:1 (large/UI).
- **Text-on-swatch** legibility: pick near-black `#15150F` or white — whichever has the **higher WCAG
  contrast ratio** with the swatch (crossover ≈ luminance 0.2). *Not* a 0.5-luminance threshold: for
  mid-greys (luminance 0.2–0.5) dark text is objectively more legible (e.g. `#B0B0B0` → black 9.7:1
  vs white 2.2:1), and the warm near-black keeps text from vibrating on saturated brights.

If any constant or formula changes, bump dataset/app version and note it in CHANGELOG.

## 8. Version history & workflow (no drift)

- **Git from day one.** `main` is always deployable. Work on short-lived `feat/*`, `fix/*`, `docs/*` branches.
- **Conventional Commits**: `feat:`, `fix:`, `docs:`, `refactor:`, `chore:`, `test:`. Imperative mood.
- **Semantic Versioning** for the app and the dataset (independent versions). The **web app stays on `1.x`**; **`v2.0` is reserved for the native app** (`docs/IOS_APP_PLAN.md`) — ship web features as minor bumps, not a 2.0.
- **CHANGELOG.md** in Keep a Changelog format; update it in the same PR as the change. Once the
  native `2.x` stream exists, a release moves **only its own stream's entries** out of
  `[Unreleased]` (CLAUDE_NATIVE.md §6).
- **Tags** mark releases (`v0.1.0` = approved plan + mockup baseline).
- **Release checklist (cutting a version):** bump `package.json` and `APP_VERSION` in `src/js/version.js`, move the old `WHATS_NEW` (its version, date and lines) to the front of `EARLIER_NEWS`, and write the new version's `WHATS_NEW` lines and date beside it (tests fail when the versions differ, or when a released version since 1.13.0 is missing from the log) → turn CHANGELOG `[Unreleased]` into the
  release heading → refresh README's Status paragraph → add the release line to PLAN.md §5 (+ its "Current
  status" stamp) → tag (from a clone, or Actions → *Tag release* — remote sessions can't push tags). `scripts/check-docs.mjs` (CI) enforces the mechanical parts — version (README and `version.js`), dataset
  counts, the §4 tree — so a stale README fails the build instead of shipping.
- **One concern per commit.** If a change touches design tokens, it updates §3 here too.
- Deploy = push `src/` to GitHub Pages via `.github/workflows/deploy.yml`; Squarespace **links** to it (an inline iframe needs the Business plan). See `docs/EMBED.md`.
- **Service-worker discipline (learned the hard way — broke the live site twice).** GitHub Pages serves assets with `cache-control: max-age=600`, so a plain network-first SW can still hand a browser a *stale* `app.js` against a fresh `index.html`. Rules: (1) **bump `CACHE` in `src/sw.js` on every shell/asset change**; (2) the SW is **network-first for the app shell** (navigations + same-origin JS/CSS) and fetches it with **`{cache:'reload'}`** to bypass the HTTP cache (fonts/dataset stay cache-first); (3) `index.html` **auto-reloads once on `controllerchange`** so a new SW can't leave a mismatched shell; (4) only a navigation to the **app itself** (`/` or `/index.html`) is cached as the shell — any other page in scope (`privacy.html`, `support.html`) caches under its own URL, or one visit to it would replace the offline copy of the app. After deploying, hard-refresh and confirm `palette.ryanmette.com/sw.js` shows the new `CACHE`.

## 9. Definition of done (every milestone)

A change is done only when:
1. It conforms to this file (design tokens, architecture, color science).
2. CHANGELOG updated; commit messages follow §8.
3. Pure-math modules have unit tests passing (from M2 on).
4. UI meets WCAG AA (keyboard + contrast + focus checked).
5. No new runtime dependency unless added to §6.
6. The tool still runs as a plain static file with no server.
7. Docs still tell the truth: user-visible behaviour changed → README / USE_CASES / PLAN checked in the
   same PR (or explicitly untouched for a reason). `scripts/check-docs.mjs` gates the mechanical claims.

## 10. Anti-drift guardrails — do NOT
- Add a framework/build tool to the *runtime* path.
- Hardcode colors/sizes outside the §3 token set.
- Ship paint data without provenance in `SOURCES.md`.
- Imply a paint match is exact (always show ΔE + label).
- Introduce a backend, accounts, or storage of personal data.
- Let this file fall out of sync with the code. Update it in the same commit.
