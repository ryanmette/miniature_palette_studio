What’s new: a dot on ⋯, and a notification log

About shows “What’s new in 1.13.0” now (PLAN §5 item 39). But a painter finds it only if they open About. This study does two things. Part A specifies a small dot on ⋯ after an update, ready to build. Part B studies a notification log next to ⋯, which Ryan asked to study later (help-about.html, answer 5). Nothing here is built.

Page theme

0What we have now (measured, v1.13.0)

  • What’s new is a list of 4 short lines in About (version.js WHATS_NEW). A test makes sure that its version is the app’s version.
  • The app does not remember a version. No pref holds “the last version this device saw”, so the app cannot know that an update came.
  • The way to About is 2 taps: ⋯ → Help & info → About. The footer has an About link too, at the end of a long page.
  • The header (measured in Chromium, both themes): at 360px it has two rows (116px). The top row holds the wordmark and ⋯, with 142px free between them. At 768px and 1180px it is one row with 244px and 662px free. ⋯ is 44 × 44 on touch and 38 × 38 with a mouse.
  • Toasts last 1.7 seconds. They are aria-hidden, and say() speaks the same words into a live region. After 1.7 seconds there is no way to read a toast again. Part B comes back to this.

1The rules we must keep (primary sources)

Apple, Human Interface Guidelines → Notifications (read 2026-10-29)

“Use a badge only to show people how many unread notifications they have.”
“Make sure badging isn’t the only method you use to communicate essential information.”
“Avoid creating a custom image or component that mimics the appearance or behavior of a badge. People can turn off notification badges if they choose, and will become frustrated if they have done so and then see what appears to be a badge.” — developer.apple.com/design/human-interface-guidelines/notifications
  • What this means for us. Apple’s “badge” is the red oval with a number on an app icon. In the iPhone app, a red counter in our header looks like that badge. So the dot has no number and no red. It is a small dot in the accent colour, and it is never the only way to find What’s new (About always has it).
  • WCAG 2.1, 4.1.2 Name, Role, Value: a screen reader must hear what the dot shows. The dot is a picture, so ⋯’s accessible name must change with it.
  • WCAG 2.1, 1.4.11 Non-text Contrast: a graphic that carries meaning needs 3:1 against what is next to it. --accent on --bg is 6.34:1 in light and 6.61:1 in dark, so it passes.
  • WCAG 2.1, 1.4.1 Use of Color: the dot is a shape that comes and goes, not only a colour change. It passes.
  • Our own rules. §1: no server, so the app can know only what this device knows. §3.4: nothing moves when the dot shows (it floats inside ⋯’s box), and a change that the painter did not make does not bounce. §3.5: a colour has one meaning. --danger means failing or destructive, so the dot is not red. §3.6: the header holds only the mode switch and ⋯, and a new header control needs a line there first.

The Material Design 3 page on badges (m3.material.io) was not reachable from this session, so it is not quoted here.

AThe dot on ⋯ (ready to build)

Three directions. Each one shows a dot after an update. They are different in when the dot goes.

A1 · Dot until About opensToo sticky — a painter who opens ⋯ for the theme and closes it sees the dot again and again, so they learn to ignore it.
A2 · Dot on ⋯, “New” on AboutRecommended — the dot leads to ⋯ and goes when ⋯ opens. Inside, a “New” tag on About leads the rest of the way, and stays until About opens or the next update.
A3 · About opens by itselfNo — a modal on load gets between the painter and their scheme (principle 3, one click to value), and it takes focus away from what they came to do.

A2, step by step (try it)

  1. After an update, ⋯ shows the dot. Its name becomes “Settings – what’s new in 1.14”, so a screen reader hears it.
  2. Press ⋯. The dot goes, and the name is “Settings” again. In the Help & info group, About has a New tag.
  3. Press About. What’s new is near the top, under one paragraph about the app. The tag goes. Nothing shows again until the next update with new lines.
  4. A painter who never opens ⋯ keeps the dot. It does not move, pulse or grow: it waits.

BA notification log next to ⋯ (study only)

A log is a list of things that happened, kept so that you can read them later. With no server (§1), the app can log only what this device knows. So the first question is: what would the log hold?

What the device knows, and where the painter sees it now

EventWhere it shows nowDoes a log help?
An update with new linesAbout (and Part A’s dot)Little. Part A covers it.
A toast (“Imported 120 paints · 3 not found”, “Saved as X”)1.7 seconds, then goneYes. This is the one gap. A long toast is hard to read in 1.7 seconds, and an import result is worth reading again.
The shelf could not be saved (private mode, storage full)Nowhere. store.js persist() drops the error.Yes, but a log is the wrong place: a painter who loses their shelf must see it at once (a note, not a list).
The last backup is oldNowhere. The app does not record when it made a backup.Maybe. It needs a new pref (the date of the last backup).
New paint data (the dataset version changed)About shows the version onlyMaybe. The app would need to keep the old version, and data release notes to show.
Another tab changed the shelfThe page repaintsNo. The change is visible.
A list link or a “bought” link was openedA confirm, before anything changesNo. The painter chose it seconds before.
  • The finding: most events already have a better home. The log’s real content is recent toasts. Two other items (save failure, old backup) are notices that deserve their own place.
  • Apps with a bell (an inbox next to the menu) have a server that sends things to you: replies, mentions, invites. We have none of that, so our bell would be empty most days. An empty bell teaches people to ignore it.

Three directions

B1 · No logRecommended now — build Part A. Make toasts longer (below). Give a failed save its own note. Nothing in the header changes.
B2 · “Recent” in ⋯Maybe later — the last 5 toasts of this visit, in memory (no new saved data), in ⋯ above Help & info. It costs no header space. It shows only when it holds something.
B3 · A bell next to ⋯No — it fits (142px free at 360px), but it is empty most days, and in the iPhone app a counter looks like the system badge that Apple tells us not to copy.
  • The cost of B3 in the header: a second icon button beside ⋯, a second popover with its own focus and Esc rules, a third elevation user (§3.4 allows it), and a §3.6 change (“the header holds only the mode switch and ⋯”). The cost is real for a list that is mostly empty.
  • If B2 is built, it is a list (ul), not a live region. say() already speaks each toast. Each row has its time as text. The group has a reserved height (§3.4), or it is last in ⋯, so that it does not push the other rows down when it fills.

5Recommendation and questions

Recommendation: build A2 (a dot on ⋯, a “New” tag on About) as one small PR. Do not add a bell (B3). Fix the two gaps that Part B found, without a log: (1) a toast stays long enough to read, and (2) a failed save shows a note. Come back to B2 (“Recent” in ⋯) only if painters ask for a toast again.
