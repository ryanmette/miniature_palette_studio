“Use my paints” and the ⋯ menu

Part 2 (2026-10-27): the full ⋯ menu, from a menu audit, is the last section on this page.

The question: should Use my collection (Off · Prefer owned · Only owned) move from the Plan tab to the global ⋯ settings menu? Short answer: yes, with one condition — the live palette must say when the setting is on, because it changes the paints you see there.

What the setting does today (matchOpts() in app.js): Prefer owned ranks each owned paint as if it were ΔE 6 closer (OWNED_BOOST; the ΔE you see stays true). Only owned keeps only owned paints in the search. It ranks the live palette, the Plan and the Accessibility swap. It does not change Equivalents. It is saved on your device (store.setPref('collection')), and a share link does not carry it. But its only control is in the Plan tab, two screens below the palette on a phone.

Paint names and ΔE values in the frames come from the real dataset: the target colours are the Alga Green scheme (#555E1B · #241B5E · #C8A13A), and the example shelf holds 23 common Citadel paints, with no dark blue or purple. I read every value from the running app with that shelf, so the frames show what the app really does in each state.

Why these choices

  • Why below the palette, not next to its label. I put a chip after “Live palette → nearest paint” in the real app and measured it. At 1280px it pushed undo, redo, + and Ideal|Real down to a second row (header height 36 → 74px). On a phone it needed its own row anyway. Below the palette, it fits on one line at every width, and it sits right under the paint names it explains.
  • Why a full-width button, not a small pill. It is a control as well as a status, so it must be 44px tall on touch (§3.6). On desktop it uses the normal 38px --tap.
  • Contrast. The usual badge pair, --success text on --success-weak, is only 3.0:1 in the light theme. That fails WCAG AA for 12px text. So the note’s text uses --text on --surface (14:1). Only the ✓ glyph is green: 3.3:1 light and 6.3:1 dark, which passes the 3:1 limit for graphics.
  • No jiggle (§3.4). The note appears only after you change a setting, never on hover or select, and it can only push content down. Changing the setting already redraws the paints, so the page does not move in a surprising way.
  • Keyboard and screen readers. The note is a <button aria-haspopup aria-controls="settingsMenu"> with an accessible name such as “Use my paints: prefer owned. Change”. Opening ⋯ from it moves focus to the selected option, and Esc returns focus to the note, not to ⋯. A change is announced through the existing live region. In the empty-shelf state the note opens the Shelf instead, so it drops aria-haspopup and its name says so: “Use my paints: prefer owned, but you own no paints yet. Open Shelf”.
  • Nothing else changes. The setting is still saved per device. A share link still does not carry it, so a friend who opens your link sees matches from their shelf. That is correct.
  • Constitution change (§3.6). The header bullet would say that the ⋯ popover holds theme, locale, Use my paints (off · prefer · only — a saved personal setting that ranks every stage, shown on the live palette by the matching note when it is on), Export list / Share link, and About & data. It would also remove “the Use my collection control lives in the Plan tab”.

Verdict: one setting, in one place, next to the other personal settings, plus an honest sign where its effect shows. Off costs nothing. On tells you why a paint you own beat a closer one.

B · The control lives on the palette, and ⋯ does not have it

The Off · Prefer · Only control sits below the live palette all the time, in place of the note.

Pro: one tap, and you see it where it acts. Con: a row of 44px controls stays in the studio forever, also for the many people who own nothing. It also looks like a per-scheme choice, but it is a saved preference. §3.6 sends preferences to ⋯ for this reason.

C · Only in ⋯, with no sign on the palette

The same ⋯ row as A, but without the note.

Pro: the cleanest studio. Con: you turn on Only owned once, forget it, and a month later your accent is “Loose” and nothing says why. That breaks principle 4, “Explain, don’t mystify”, and principle 2, “Honest about approximation”. Not recommended.

Decisions (Ryan, 2026-10-26)

  • Direction A is chosen: the setting moves to ⋯, and the matching note shows on the live palette when it is on.
  • The label is “Use my paints” (Off · Prefer · Only). It is short enough for a phone. “Use my shelf” was not chosen, because the shelf also holds to-buy paints.
  • Equivalents ignores the setting. It compares brands, so it must list every brand. Owned paints already show ✓ in that list.
  • Empty shelf: the note says “Open Shelf” and opens the Shelf. In every other state it says “Change” and opens ⋯.

The full ⋯ menu Proposal · from the menu audit

Ryan asked if other things belong in ⋯. An audit read the code and the docs, fetched primary sources (Apple HIG, the Android design guide, MDN, WCAG) and judged every candidate three ways: the constitution, the painter, and the platform. All three judges agreed on the shape below: two new rows and one new button, and fix the menu container first. Everything else stays where it is, moves into About & data, or waits.

More

Fix the container first (problems in the menu today)

  • It says “menu”, but it is not one. The panel is role="menu" and ⋯ says aria-haspopup="menu" (index.html), but it holds a switch, segmented groups and buttons, not menu items. A screen reader then expects a list of commands that you move through with the arrow keys. It becomes a non-modal dialog named “Settings”, with aria-haspopup="dialog". Focus moves into it when it opens and returns to ⋯ when it closes.
  • Touch targets are too small. Export list, Share link and About & data use .btn.sm, a fixed 32px. §3.6 asks for 44px on touch. Every control uses --tap instead.
  • It cannot scroll. .popover has no height limit, so a taller menu runs off a short screen. The menu gets a max-height and scrolls inside itself.
  • Wrong shadow tier. It uses --shadow (in-page). §3.4 gives floating overlays --shadow-pop.
  • Labels are not localised. Theme, Language, Scheme, More and the button labels have no data-i18n. Every row, old and new, gets one (§4 i18n).

Not in the menu, and why

CandidateWhere it goesWhy
Include ContrastStays in PlanIt decides how a role gets painted (one-coat base), and that thinking happens in the Plan. A Contrast paint in the palette already shows its finish icon, so it is not silent.
Tone ladderStays in PlanIts rungs show on the Plan cards, next to the control. Apple and Android both say: keep task options on the screen they affect.

Privacy linkStays in About & dataApp Store rule 5.1.1(i) (“within the app in an easily accessible manner”) is already met there. Help links to it too.
Install the appNot nowThe install prompt event works only in Chromium browsers (MDN). iPhone has no such event, so the row could only show instructions.
Brands I useNot nowPLAN backlog 8 puts a brand limit on the substitute finder, as a choice you make at that moment. A hidden app-wide filter is the same silent-matching problem the note fixes.
Reduce motion switchDroppedThe app already follows the phone’s setting. Apple: “don’t include redundant versions” of system settings. WCAG 2.3.3 is AAA, and the media query alone meets it.

Open questions for you

  • Help in ⋯. Two judges want a Help button next to About & data. The third measured that two new buttons (Privacy and Help) pushed the old menu off a 360px screen. With the new phone layout, one Help button fits. Keep it?
  • Contrast in the matching note. Should the note under the palette also show when Include Contrast is on (for example “Contrast paints included”), not only when Use my paints is on?
  • Keyboard shortcuts. Show that section only on a device with a keyboard (as drawn), or always?
